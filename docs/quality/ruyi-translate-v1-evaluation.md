# 如意翻译第一版质量评测方案

状态：已确认，发布前必须建立基线
方案版本：`ruyi-evaluation-v1`

## 1. 目的和适用范围

本方案用于判断标准模式、精译模式、术语库和并发加速是否在可接受的等待与费用下减少翻译错误。结果只能说明某个明确版本在固定语料和条件下相对基线的表现，不能证明译文绝对正确，也不能转换成面向用户的“准确率”。

持续集成不调用真实模型。真实请求只由开发者在受控环境中手动运行，使用合成、公开许可或已获授权的数据。输出经检查后才可作为开发测试资产。插件运行时不包含、不读取、也不写入评测缓存；缓存机制不得进入发布包，不能被当作翻译历史使用。

在完成 §10.1 的首轮基线、冻结数据集版本并填写基线记录前，项目不能进入发布候选状态。

## 2. 第一版必须回答的问题

1. 标准模式是否稳定遵守目标语言、结构保护和术语规则？
2. 精译模式在相同服务、模型、协议、参数和输入条件下，是否比标准模式减少误译、漏译、多译和术语错误？
3. 精译修订是否会把正确初译改坏，伤害集中在哪些问题类型？
4. 并发加速是否缩短长文本完成时间，同时维持跨段术语、指代、格式和文体一致性？
5. 源文、术语、目标语言、行业配置、参考译例、分析结果和审校建议中的指令注入，能否改变角色或输出契约？
6. Chat Completions 与 Responses 是否被归一化成一致的文本、完成、取消和错误状态？
7. 不同模型、语言方向和行业下，质量、等待、token 和调用次数是否仍符合本文件的门槛？

只有同一服务端点上的同一模型同时支持两种协议时，才比较两种协议的译文行为。使用不同模型或供应商时，只测试本地适配器的请求映射、事件解析和统一错误，不宣称译文等价。

## 3. 数据集范围和最低规模

### 3.1 完整质量集

完整质量验收包括：

- 简体中文 → 英语；
- 英语 → 简体中文。

每个方向的冻结核心集至少包含 100 篇文本、500 个可独立标注的段落，并在下列五类中各包含至少 15 篇，其余样本可按风险补充：

- 通用说明和日常书面文本；
- 软件开发文档、错误信息和 README；
- 学术摘要和方法说明；
- 电力能源运行、设备和技术报告；
- 法律合同条款。

每个方向至少有 10 篇规范化后达到 8,000～10,000 个 Unicode 码点的文本，用于全文和并发分块配对测试。不能通过重复短句凑长度。

### 3.2 基本功能集

以下语言到简体中文分别至少包含 30 篇文本、100 个段落：

- 日语；
- 韩语；
- 法语；
- 德语；
- 西班牙语。

该集合只验证目标语言、结构、协议和基本可用性。后续若要宣称完整质量能力，必须按 §3.1 建立该语言方向的核心集。

### 3.3 专项集合

专项样本可以与核心集重叠，但必须单独标记：

- 至少 100 个术语样本，覆盖多义、重叠、同级冲突、别名、大小写、六个以上术语、严格术语、允许变体、禁止译法和语境不适用；
- 至少 100 个结构样本，覆盖 Markdown、表格、链接、代码围栏、行内代码、命令、路径、URL、邮箱、数字、日期、单位和占位符；
- 至少 100 个提示注入样本，均匀放入源文、目标语言、术语、行业配置、参考译例、附加要求、分析结果和审校建议；
- 至少 40 个跨段样本，覆盖代词、省略、重复术语、专名和文体一致性；
- 10,000 码点边界、Emoji、组合字符、CRLF、不可切分单元、流中断、截断和多余输出等协议与边界夹具。

不得使用未获授权的真实个人、公司或客户数据。语料必须区分 `synthetic`、`public-licensed` 和 `authorized-private`；最后一类不进入版本库或共享缓存。

## 4. 测试资产格式

语料使用带版本号的 JSONL。每条至少包含：

```json
{
  "schemaVersion": "evaluation-case.v1",
  "caseId": "energy-en-zh-0001",
  "sourceLanguage": "English",
  "targetLanguage": "Simplified Chinese",
  "evaluationDomain": "energy",
  "domainProfileId": "power-energy-v1",
  "documentType": "technical-report",
  "source": "...",
  "references": ["..."],
  "segments": [
    {"id": "p-1", "ordinal": 0, "sourceStart": 0, "sourceEnd": 120}
  ],
  "terms": [
    {
      "id": "term-1",
      "sourceLanguage": "English",
      "targetLanguage": "Simplified Chinese",
      "source": "unit commitment",
      "preferredTarget": "机组组合",
      "allowedVariants": [],
      "forbiddenTargets": ["单位承诺"],
      "aliases": ["UC"],
      "meaning": "电力系统中确定机组启停组合",
      "strictness": "preferred",
      "caseSensitive": false,
      "priority": 100,
      "origin": "domain",
      "applies": true
    }
  ],
  "protectedItems": [
    {
      "id": "protected-1",
      "segmentId": "p-1",
      "type": "placeholder",
      "value": "{plantId}",
      "sourceStart": 80,
      "sourceEnd": 89
    }
  ],
  "referenceTranslationIds": [],
  "expectedIssues": [],
  "specialtyTags": ["terminology", "structure"],
  "privacyClass": "synthetic",
  "notes": "..."
}
```

`evaluationDomain` 使用 `general`、`software`、`academic`、`energy` 或 `legal`，用于从实际用例重新计算五类领域数量；`specialtyTags` 使用 `terminology`、`structure`、`injection`、`crossSegment` 或 `boundary`，用于重新计算专项集数量。`references` 与 `referenceTranslationIds` 一一对应。若填写 `expectedIssues`，每项必须包含唯一 ID、存在的分段 ID、错误类别、严重度、落在该分段内的源文码点范围和简短说明，不能只保存无法核对的自由 JSON。同一语言方向中，只改用例 ID、大小写或空白的重复原文会被拒绝，不能用复制短句凑语料数量。

术语匹配层另有冲突、别名、大小写、边界和优先级夹具，不能只依赖真实模型输出验证本地规则。

## 5. 真实输出缓存和请求指纹

开发评测缓存可以保存模型输出、经过允许的响应元数据、token 用量和时间统计。不得保存 API Key、`Authorization`、账户 ID、供应商组织信息、未经授权的数据或未经清理的错误对象。

缓存只允许存在于明确的开发测试目录，并且只有 `synthetic` 或 `public-licensed` 数据可以进入版本库。构建测试必须证明发布资源中不存在该目录、缓存加载器或缓存写入路径。

请求指纹使用规范化对象的 SHA-256，至少包含：

```text
provider-type + service-config-id + normalized-translation-url
+ adapter-build-version + protocol + model + reported-model-version
+ prompt-version + schema-version + evaluation-version
+ quality-mode + thinking-mode + request-parameters
+ normalized-target-language + termbase-version + domain-profile-version
+ reference-translation-ids + source-case-id
+ segmentation-mode + chunking-version + concurrency
+ canonical-request-body-hash
```

指纹不包含密钥本身。完整翻译 URL、目标语言、分块方式或并发数不同，必须视为不同条件。旧缓存只能在指纹完全相同且服务明确报告相同模型版本时复用；否则重新生成或标为不可比较。

发布判定不能只相信报告中手工填写的计数、哈希或“通过”布尔值。严格检查必须读取一个版本化证据清单，核对最终报告和实际 JSONL 用例的 SHA-256，并逐项核对自动检查、模型输出、配对样本、人工评审、修订、并发、性能和三平台记录的文件哈希、记录数量、候选版本、Git commit 与数据集版本。每条记录还必须引用一个独立原始证据附件；检查器读取附件并核对字节数和 SHA-256。三平台记录共同引用同一个按候选版本命名的 UPXS 文件，保存同一份构建输入清单哈希，并记录该文件已由对应平台的 uTools 实际安装；严格检查会在生产构建后重新计算当前 `dist` 的构建输入哈希。模型输出不得以重复用例和相同请求指纹凑数，并发和性能样本的条件、时段与序号必须唯一，人工评审须绑定具体模型输出并由独立标签重算一致率、Cohen's kappa 和裁决结果。证据记录本身只保存用例 ID、指纹、计数、状态、时间和内容哈希等审计元数据，不保存完整源文、译文、术语、参考译例、密钥或未经清理的错误对象；可能含受控原文或输出的附件不得提交到版本库。配对记录中的无术语条件使用 `termbaseVersion = "none"`，正确适用和不适用条件分别使用 `applicable:`、`inapplicable:` 开头的版本标识，以便检查器在不读取术语正文的情况下确认只改变了预定因素。UPXS 的签名格式由 uTools 控制，仓库检查器不声称能独立解析或验签；签名被接受的依据是三个平台的实际安装记录，测试人仍须对实机证据的真实性负责。

## 6. 配对评测条件

评测优先使用配对设计：同一源文只改变一个待研究因素，其余服务、模型、协议、参数、思考模式、术语、行业配置、参考译例和分块方式保持一致。

每个候选版本至少包括：

| 比较 | 两侧条件 |
| --- | --- |
| 质量模式 | 标准 / 精译 |
| 术语 | 无术语 / 正确适用术语 / 随机或不适用术语 |
| 参考译例 | 0 条 / 3 条；第 4 条由输入校验拒绝 |
| 行业配置 | 用户明确选择 / 未选择；推测领域不得自动替换用户选择 |
| 分段 | 全文 / 相同文本并发分段 |
| 思考模式 | DeepSeek 官方关闭 / 开启 |
| 协议 | 同一模型可用时 Chat Completions / Responses |

标准和精译都必须覆盖无术语、正确术语和不适用术语，不能只给精译使用更有利的术语条件。全文与分段比较必须使用相同提示词版本和相同任务资料。并发数 1、默认 3 和上限 6 各有本地模拟服务测试；真实性能基准至少比较全文、并发 2、3、4。

## 7. 自动检查

### 7.1 契约和安全

每次运行验证：

- [`ruyi-translate-v1.schema.json`](../prompts/ruyi-translate-v1.schema.json) 可由实现选定的校验器加载；
- 输入联合体、未知字段、Schema 版本、任务 ID 回显、ID 唯一性、交叉引用和集合分区；
- Unicode 码点范围、Emoji、组合字符和越界证据；
- 自定义目标语言和所有不可信字段的注入夹具；
- 分析只返回范围而不回显大段源文；
- 准确性问题的源文与译文范围属于对应段落；
- 语言审校不报告源文误译、漏译、多译或源格式错误；
- 修订只改变风险段，问题 ID恰好分为已解决和未解决两组，空替换只通过许可分支；
- 两个审校角色并行启动，分析一次，修订至多一次；
- Chat Completions 和 Responses 的输入、普通响应、流事件、完成、取消及统一错误映射；
- Bearer 和无鉴权请求头、同源重定向和跨域阻止。

静态和运行时测试还必须证明：插件没有剪贴板读取、监听或轮询；不自动建立翻译记忆；不调用 Batch API；不上传遥测、日志或本地性能汇总；运行时不读取或写入评测缓存。

### 7.2 内容和结构

每个译文执行：

- 目标语言识别；
- 数字、日期、单位、URL、邮箱和占位符多重集比较；
- Markdown、代码围栏、行内代码、链接和表格结构检查；
- 段落 ID、缺块、重复块和顺序检查；
- 严格术语命中、禁止译法和允许变体；
- 推荐术语命中及“不适用”豁免；
- 已知多余前缀、固定提示词片段和输出契约破坏；
- 流是否正常完成、响应大小和输出码点上限。

字符命中不能单独证明术语正确。存在屈折变化时记录 lemma 或允许变体命中，并由人工判断语境、词形和语法。目标语言识别同样是启发式指标，只有在冻结评测集上校准后才用于风险提示，不能独自证明译文正确。

### 7.3 机器翻译指标

可以记录 chrF、COMET、XCOMET 或 CometKiwi，但必须固定工具和模型版本，说明是参考指标还是无参考质量估计，并与人工错误标签一起解读。BLEU 只作历史辅助。任何单项分数都不能显示为产品“准确率”，也不能替代人工抽查。

## 8. 人工评价

### 8.1 错误标注

按段落标记：

- 准确性：误译、漏译、多译；
- 术语：正确、允许变体、语境不适用、错误、漏用；
- 流畅度：语法、搭配、自然度；
- 文体：受众、语气和行业习惯；
- 一致性：跨段术语、专名、指代和格式；
- 结构：数字、链接、占位符、代码和 Markdown；
- 严重度：`critical`、`major`、`minor`。

“术语字符串出现”与“术语在当前语境、词形和语法上正确”分别判断。项目内部为便于配对统计，使用 `critical = 25`、`major = 5`、`minor = 1` 的错误分值；该权重是本项目的发布判定规则，不声称是通用行业标准。报告同时保留原始问题数，不能只报加权总分。

### 8.2 盲评

- 标准和精译随机排序，隐藏模式、模型和版本；
- 核心集至少由两名具备目标语言能力的评审独立标注；
- 法律、电力能源等高风险样本至少有一名熟悉该领域的评审；
- 分歧由第三人裁决，或在无法裁决时标为未决并排除发布结论；
- 报告简单一致率和 Cohen's kappa；
- 模型自评不能代替人工评价。

### 8.3 修订效果

对每个修订段落记录：

- 初译有问题且修订正确解决；
- 初译有问题但修订无效；
- 初译正确而修订引入新错误；
- 只改变文体且没有准确性变化；
- 审校问题被修订角色拒绝或未解决。

修订伤害率定义为“修订后新增准确性、术语或结构错误的段落数 ÷ 所有被修订段落数”。解决伤害比定义为“被正确解决的问题数 ÷ 修订新增的问题数”；新增问题为 0 时记为无穷大并单独报告。

## 9. 性能与费用

每个条件记录首个译文码点时间、完成时间、P50、P95、输入/输出/推理 token、调用次数、并发块数、取消率、超时率、修订触发率，以及服务实际返回或评测外部计算的费用。

产品内不维护会过期的价格表。评测报告可注明日期和当时价格，但费用与质量分开呈现。

对 8,000～10,000 码点文本，必须同时报告全文和并发分段：

- 首个可读结果和全部完成时间；
- 术语、指代和文体一致性；
- 缺块、重复和格式错误；
- token 与调用次数增量；
- 429、取消和超时情况。

10,000 码点是否“等待过长”取决于模型生成速度、目标语言长度、精译调用数、网络和限流，不能只由码点数判断。产品以最近本地样本估算，并在预计超过 45 秒或无样本且超过 4,000 码点时建议并发；评测用真实 P50/P95 校验该提示是否合理。

## 10. 发布门槛

### 10.1 首轮基线门槛

发布候选前必须完成并保存一份带评测日期的 `baseline-v1` 记录，包含：

- §3 的最低语料数量和数据版本；
- 默认 DeepSeek 配置及至少一个自定义服务配置的模型、端点、协议和报告版本；
- 标准、精译、全文、分段和思考开关的实际样本数；
- 人工错误、术语、结构、注入、性能、token、费用和修订伤害结果；
- 评审者数量、一致率和未决样本；
- 所有未达到下列门槛的项目及处理决定。

缺少任一项时，文档状态保持“待建立基线”，不得仅凭演示效果提交市场。

### 10.2 功能和安全硬门槛

- 自动测试、Schema 加载、协议、入口、鉴权和取消测试全部通过；
- API Key 不出现在页面状态、日志、错误、快照、评测缓存或构建产物；
- 100% 注入夹具不能改变角色、输出契约或本地设置；
- 100% 已知占位符、URL、代码和关键数字破坏被本地检查发现；
- 分块缺失、重复和乱序 100% 被发现；
- 跨域重定向 100% 在发送密钥和源文前停止；
- 运行时没有翻译历史、遥测、远程日志、评测缓存或自动翻译记忆写入；
- 恢复设置后，插件可控制的全部本地 key 均无法读取；对于已由 uTools 同步的远端或其他设备副本，只验证界面如实提示，不能把远端删除列为插件保证。

### 10.3 核心质量门槛

在冻结的中英双向核心集上：

- 最终译文不得存在人工发现但应用完全未提示的 `critical` 错误；
- 精译模式的 `critical` 数不得高于配对标准模式；
- 精译的准确性、术语和结构加权错误分值点估计至少比标准模式低 5%，且按文本自举得到的 95% 置信区间上界不得显示精译比标准差 2% 以上；
- 精译修订不得引入 `critical` 错误，修订伤害率不超过 5%，解决伤害比至少为 3；
- 适用的严格术语不得出现未发现的违反；推荐术语的适用样本中，首选或允许变体命中率至少为 95%，同时单独人工检查词义和语法；
- 禁止译法出现时必须全部被发现；
- 基本功能集不得出现目标语言完全错误、协议破坏或未发现的严重结构损坏。

若候选模型版本变化，上述结论必须重新生成，不能沿用旧模型缓存。

### 10.4 并发加速门槛

在长文本配对集上：

- 不得增加 `critical` 错误或出现未发现的结构破坏；
- 加权质量错误分值不得比全文模式高 5% 以上；
- 默认并发 3 的完成时间 P50 至少比全文模式缩短 20%，否则该配置不应触发“建议加速”；
- 输入和输出 token 合计不得超过全文模式的 1.35 倍；超过时必须在界面说明额外消耗，且不能默认建议；
- 缺块、重复块和错序率必须为 0。

真实服务波动较大，性能门槛至少在三个不同时段重复采样并报告样本数。若质量通过但速度未达门槛，可以保留用户手动开关，但不得宣称该服务配置下能够加速。

### 10.5 三平台门槛

Windows、macOS、Linux 分别实测：

- 文本匹配和全局快捷键；
- 普通隐藏后的尽力继续、取消和通知；
- 用户主动复制与粘贴回原窗口；
- 深浅主题、键盘操作和状态可访问性；
- HTTPS 与本地 HTTP 回环服务；
- 结束进程并启动新进程后无法恢复当前翻译，且数据库、文件、日志和遥测中没有源文、译文或临时术语残留。

后台网络完成和系统通知不作必达承诺；验收记录实际行为和平台差异。
